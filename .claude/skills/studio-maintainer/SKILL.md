# Studio Maintainer

This skill maintains the **framework**, not video content. It exists because the
studio separates two things that used to live in the same files:

- **Templates** (`.claude/templates/`) — committed source of truth = the harness.
- **Materialized runtime files** (`scripts/CONTEXT.md`, `animations/design-system/*`,
  `theme.ts`, `style.css`, …) — gitignored, generated by `materialize.py`, **owned
  by the user**, free to diverge as their project evolves.

That separation gives the user freedom but creates one trade-off: a harness
improvement to a template does NOT automatically reach an already-configured
project (its runtime file is frozen and user-owned). **This skill is the tool
that manages that trade-off.**

## Invariants (never violate)

The template system is held together by four things that must stay in sync:

1. **Templates** live at `.claude/templates/<path>`, mirroring the runtime path.
2. **Placeholders** are dotted config paths: `{{design.palette.bg_deep}}`,
   `{{audience.profile}}`. The renderer (`materialize.py`) is generic — it needs
   NO edits to support a new placeholder, only a config value to fill it.
3. **`.claude/templates/manifest.json`** (`paths` array) lists every file the
   renderer materializes. A template not in the manifest is never rendered.
4. **Every placeholder must have a config value.** The schema documented in
   `project-setup` Step 4.2 (`design:` block etc.) must cover every placeholder,
   or `materialize.py` aborts fail-loud.

The renderer lives at `.claude/skills/project-setup/scripts/materialize.py` and
runs in that skill's venv (`bash .claude/skills/project-setup/scripts/setup.sh`).

## Capability A — Add or modify a templated file

When a file should become templated (or an existing template gains a new
project-specific value):

1. **Template**: create/edit `.claude/templates/<path>`. Replace every
   project-specific value with a `{{dotted.config.path}}` placeholder. Keep the
   generic structure (workflow rules, universal principles) literal.
2. **Manifest**: add `<path>` to the `paths` array in `manifest.json` (skip if
   already listed).
3. **Config schema**: add any NEW placeholder's key to the `design:` (or other)
   block documented in `project-setup` SKILL.md Step 4.2, so future setups fill
   it. Pick a clear dotted name; lists render comma-joined.
4. **Git**: if the runtime path is newly templated, untrack it and ignore it —
   `git rm --cached <path>`, add an anchored `/​<path>` line to `.gitignore`
   (under the "Materialized studio files" section), and add a `.gitkeep` if that
   removal empties a tracked directory.
5. **Validate**: run a dry-run against a complete config to confirm no missing
   keys (see Capability D).

To **remove** a templated file: reverse the steps (delete template, drop from
manifest, optionally re-track the runtime file).

## Capability B — Adjust the materialization flow

Changes to `materialize.py`, `manifest.json` schema, `setup.sh`, or
`requirements.txt`. After any change, re-run the validation in Capability D and a
full materialize against a synthetic complete config (temp root) to prove the
renderer still produces valid output. Keep the renderer generic — resist
hard-coding per-file logic; prefer expressing variation as placeholders + config.

## Capability C — Sync a harness improvement into a project

Goal: a template improved (e.g. a new workflow rule in a `CONTEXT.md`), and you
want it in a project whose runtime file the user has since edited — **without
clobbering their edits**.

1. **Stage** the current templates rendered with the project's own config into a
   temp tree (non-destructive):
   ```bash
   bash .claude/skills/studio-maintainer/scripts/template-diff.sh
   ```
   It renders to a temp root and prints a per-file diff of *what the current
   templates would produce* vs *what the project's live runtime files contain*.
2. **Read the diff with the user.** Separate harness changes (worth pulling) from
   the user's own project edits (must be preserved).
3. **Apply selectively** — hand-merge the harness hunks into the live runtime
   file, OR, if the user has not customized that file, just re-materialize it.
   Never blindly overwrite a user-owned runtime file.

> Rule of thumb: if an improvement is so universal it must ALWAYS propagate, it
> probably belongs in `CLAUDE.md` (committed, flows on every clone), not in a
> per-project materialized `CONTEXT.md`.

## Capability D — Validate the template system

Fail-loud check that every placeholder resolves against a config, writing
nothing:

```bash
bash .claude/skills/project-setup/scripts/setup.sh
.claude/skills/project-setup/.venv/bin/python \
  .claude/skills/project-setup/scripts/materialize.py --config <complete-config> --dry-run
```

Run this after any template, manifest, or schema change. A green dry-run against
a complete config means setup will succeed for a new project.

## Out of scope

- Do NOT produce video content (scripts, specs, compositions, renders).
- Do NOT add this skill to CLAUDE.md's routing table — it is maintainer-only by
  design.
